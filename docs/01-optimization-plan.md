## 方向 1：扩展协议横向对比

**教学目的**：学生在面试中被追问"MCP 为什么不用 gRPC / WebSocket / GraphQL"时，能从协议设计哲学高度作答，而非仅仅背诵 JSON-RPC 的优点。

#### 1.1.1 MCP（JSON-RPC）与 gRPC 的对比

**核心问题**：gRPC 使用 Protocol Buffers 做序列化，性能远超 JSON；gRPC 有强类型 IDL，IDE 支持好。为什么 MCP 不直接用 gRPC？

```
┌─────────────────────────────────────────────────────────────────┐
│               MCP (JSON-RPC) vs gRPC 设计哲学对比                │
│                                                                 │
│  维度          JSON-RPC (MCP)         gRPC                      │
│  ────────────  ───────────────────    ────────────────────────  │
│  序列化格式     JSON (文本)            Protobuf (二进制)          │
│  序列化效率     低 (文本解析+膨胀)      高 (紧凑二进制，快 3-10x)  │
│  人类可读性     ✅ 直接可读             ❌ 需工具解码              │
│  类型系统       弱 (JSON Schema)       强 (Protobuf IDL)         │
│  代码生成       无 (手写消息解析)       有 (protoc 自动生成)       │
│  HTTP/2 依赖   无 (传输无关)           强 (重度依赖 HTTP/2)        │
│  浏览器支持     ✅ 原生 fetch/SSE       ❌ 需 grpc-web 代理       │
│  调试难度       低 (curl/nc 即可)       高 (需 grpcurl/BloomRPC)  │
│  学习曲线       极低 (JSON 人人会)      中高 (Proto 语法+工具链)   │
│  生态兼容性     极高 (LSP 验证)         中 (后端微服务主流)        │
└─────────────────────────────────────────────────────────────────┘
```

**为何选择 JSON-RPC 而非 gRPC？——四个关键理由：**

**理由一：AI 工具调用的延迟瓶颈不在序列化**

```
一次典型的 MCP 工具调用延迟分解：

  JSON 序列化:    ~0.05ms   ← 几乎可忽略
  JSON 反序列化:  ~0.1ms    ← 几乎可忽略
  网络传输:       ~1-10ms   ← 非主导因素
  工具执行:       ~50-5000ms ← ★ 绝对瓶颈（数据库查询、API 调用）
  LLM 推理:       ~200-2000ms ← ★ 第二大瓶颈

结论：即使 gRPC 将序列化开销从 0.15ms 降到 0.02ms，对端到端延迟的改善 < 0.01%。
      优化序列化格式对 MCP 场景几乎没有实际收益。
```

**理由二：工具 Schema 的自描述性优先于类型安全**

MCP 的工具定义需要自描述——LLM 通过读取文本描述来理解工具的用途。JSON Schema 天然支持 `description` 字段，Protobuf 的注释在编译后丢失。

```protobuf
// gRPC：注释在编译后消失，LLM 无法读取
service WeatherService {
  // 这里写的描述，编译后 LLM 看不到
  rpc GetWeather(WeatherRequest) returns (WeatherResponse);
}

message WeatherRequest {
  string city = 1;  // 这条注释同样丢失
}
```

```json
// MCP/JSON：所有描述都是运行时可见的，LLM 可以直接"读懂"
{
  "name": "get_weather",
  "description": "获取指定城市的实时天气信息，返回温度、湿度、风速",
  "inputSchema": {
    "type": "object",
    "properties": {
      "city": {
        "type": "string",
        "description": "城市名称，支持中英文，如'北京'、'Tokyo'"
      }
    }
  }
}
```

**理由三：传输无关性 > 协议强绑定**

gRPC 重度依赖 HTTP/2，在以下 MCP 核心场景中直接不可用：

| 场景 | gRPC | JSON-RPC (MCP) |
|------|------|----------------|
| stdio 本地进程通信 | ❌ 不支持 | ✅ 原生支持 |
| 浏览器直接连接 | ❌ 需 grpc-web 代理 | ✅ 原生 fetch / SSE |
| 云函数 (FaaS) | ❌ 部分支持 | ✅ Streamable HTTP |
| curl 手动调试 | ❌ 不可行 | ✅ 一行命令 |

**理由四：LSP 生态验证了 JSON-RPC 的可行性**

LSP 自 2016 年起在 VS Code 中使用 JSON-RPC，服务了数百万开发者。每日处理的 JSON-RPC 消息量证明了这种协议在工具通信场景中的可靠性。MCP 选择同样路径是为了降低技术风险。

> **面试金句**："gRPC 是为微服务间高性能通信设计的，MCP 是为 AI 工具发现和调用设计的。两者的核心场景不同——gRPC 优化的是序列化效率，MCP 优化的是自描述性和接入成本。gRPC 让你跑得更快，JSON-RPC 让更多人愿意来跑。"

#### 1.1.2 WebSocket 与 Streamable HTTP 的对比

**核心问题**：WebSocket 是成熟的双向通信协议，为什么 MCP 新增 Streamable HTTP 而不是直接用 WebSocket？

```
┌─────────────────────────────────────────────────────────────────┐
│          WebSocket vs Streamable HTTP 在 MCP 场景的对比          │
│                                                                 │
│  维度            WebSocket              Streamable HTTP         │
│  ──────────────  ────────────────────   ──────────────────────  │
│  协议层级        独立协议 (升级 HTTP)    标准 HTTP/1.1            │
│  连接模型        持久长连接              按需连接 + 可选流式响应   │
│  穿透代理        ❌ 困难 (需 Upgrade)     ✅ 天然穿透              │
│  负载均衡        ❌ 需 sticky session    ✅ 无状态路由             │
│  Serverless      ❌ 不支持 (长连接)       ✅ Stateless 模式天然支持 │
│  断线重连        需手动实现              无需重连 (每个请求独立)   │
│  服务端推送      ✅ 原生双向              ✅ Stateful 模式 SSE 流  │
│  状态管理        隐式 (连接 = 会话)       显式 (Mcp-Session-Id)    │
│  K8s 部署       需特殊配置               标准 Deployment + HPA   │
└─────────────────────────────────────────────────────────────────┘
```

**为什么 Streamable HTTP 而非 WebSocket？——三个决定性因素：**

**因素一：企业代理/防火墙兼容性**

```
WebSocket 在企业网络中的痛苦：
  ┌──────────┐     ┌──────────────┐     ┌──────────┐
  │  Client  │ ──→ │ 企业 HTTP 代理 │ ──→ │  Server  │
  └──────────┘     └──────────────┘     └──────────┘
                          │
                    常见问题：
                    · 代理不支持 Upgrade 头 → WebSocket 直接被拒
                    · 代理空闲超时断开 WebSocket（无法配置 keepalive）
                    · HTTP/2 代理可能完全不支持 WebSocket

Streamable HTTP：
  每个请求都是标准 HTTP POST/GET，任何 HTTP 代理都支持。
  这就是为什么 HTTP 能穿透几乎所有防火墙——因为它就是 Web 本身。
```

**因素二：Serverless 亲和性**

WebSocket 要求 Server 维护长连接，这与 FaaS 的"用完即走"模型根本冲突。Streamable HTTP 的 Stateless 模式天然适配 Lambda / 云函数 / Cloud Run。

**因素三：弹性伸缩友好**

WebSocket 连接绑定到特定 Pod，水平伸缩时需要特殊处理连接迁移。Streamable HTTP 的每个请求可以路由到任意 Pod。

> **面试金句**："WebSocket 解决的是'实时双向'，Streamable HTTP 解决的是'可靠灵活'。在 MCP 的场景中，可靠性（连接可恢复）和灵活性（跨网络环境）比全双工实时性更重要。而且 Streamable HTTP 的 Stateful 模式通过 SSE 也提供了服务端推送能力。"

#### 1.1.3 GraphQL Schema Introspection 与 MCP 工具发现机制

**核心问题**：两者都解决了"让调用方知道服务方能提供什么"的问题，它们的异同是什么？

```
┌─────────────────────────────────────────────────────────────────┐
│      GraphQL Schema Introspection  vs  MCP tools/list           │
│                                                                 │
│  共同点：                                                        │
│  · 都允许调用方在运行时查询"你能做什么"                           │
│  · 都使用类型系统描述能力（GraphQL Type System / JSON Schema）    │
│  · 都支持嵌套和复杂参数结构                                       │
│                                                                 │
│  关键差异：                                                      │
│                                                                 │
│  维度            GraphQL Introspection   MCP tools/list          │
│  ──────────────  ──────────────────────  ──────────────────────  │
│  服务对象        人类开发者                AI 模型 (LLM)          │
│  描述语言        类型定义 (SDL)           自然语言 (description)   │
│  发现粒度        字段级 (field)           工具级 (tool)           │
│  语义理解        依赖开发者经验            description 驱动 LLM   │
│  更新通知        ❌ 无标准机制              ✅ tools/list_changed │
│  版本管理        ❌ 无 (需额外工具)          ✅ protocolVersion    │
│  可执行性        声明式查询                RPC 式调用              │
└─────────────────────────────────────────────────────────────────┘
```

**设计思想的分野**：

GraphQL Introspection 的设计哲学是"让机器可读的 Schema 自动生成文档"——服务人类开发者。MCP tools/list 的设计哲学是"让 AI 能自主理解工具用途"——服务 AI 模型。

这决定了最关键的差异：GraphQL 的 Schema 描述是面向类型的（`String!`、`[User!]!`），MCP 的工具描述是面向语义的（自然语言 description）。对 LLM 来说，类型约束是次要信息，语义描述才是决定是否调用工具的核心判断依据。

> **关键认知**：GraphQL 的 Introspection 和 MCP 的 tools/list 都是"服务能力自描述"模式的不同实例，但服务对象不同导致了设计路径的分野。这种区别反映了更广泛的趋势：当 API 的消费者从人类变成 AI 时，"描述质量"比"类型精确度"更重要。

---

**教学建议**：

1. 将三个对比各作为一个独立小节（2.4.1 / 2.4.2 / 2.4.3），每个控制在 1-2 页
2. 每个对比用表格 + 关键论述 + 面试金句的三段式结构
3. 课后作业：让学生用自己的话解释"为什么 MCP 选择 JSON-RPC 而不是 gRPC"，录音后自查

#### 2.1.1 脉络一：LSP 的成功——范式的证明（2016-2020）

```
LSP 的革命性贡献：从 N×M 到 N+M（同一个公式！）

LSP 之前 (2015)：                    LSP 之后 (2016+)：
                                    
  N 个编辑器 × M 种语言               N 个编辑器 + M 种语言
  = N×M 个插件                       = N+M 个适配
                                    
  Sublime × Python                   Sublime ⟍
  Sublime × JavaScript               VS Code  ─ LSP Protocol ─ Python Server
  Sublime × Go                       Vim      ⟋               JavaScript Server
  VS Code × Python                                             Go Server
  VS Code × JavaScript              
  VS Code × Go                      只需写一个 Language Server
  Vim × Python                      所有编辑器都能用
  Vim × JavaScript
  Vim × Go
  ... (N×M = 数十个插件)             (N+M = 几个编辑器适配 + 几个 Server)
```

**LSP 验证了什么？**

1. **JSON-RPC 在工具通信场景中足够好**：每天数十亿条消息，性能没出问题
2. **N×M→N+M 的公式是可行的**：生态从几十个插件爆炸到几百个 Language Server
3. **社区会自发贡献 Server**：标注化降低了门槛，激励了贡献

**MCP 直接继承了 LSP 的哪些基因？**

| LSP 基因 | MCP 继承 |
|----------|----------|
| JSON-RPC 2.0 协议 | 同协议基础 |
| 传输无关设计（stdio/TCP/HTTP） | 同设计理念 |
| Initialize → Running → Shutdown 生命周期 | 同生命周期模型 |
| Server 能力声明（ServerCapabilities） | 同能力协商机制 |
| 通知机制（PublishDiagnostics 等） | 同通知机制（Progress, Resource Updated） |
| TextDocument 抽象 | Tools/Resources/Prompts 抽象 |

> **关键洞察**：MCP 不是凭空创造的——它是 LSP 范式在 AI 工具调用领域的"搬运"。LSP 证明了"用标准协议连接工具消费者和工具提供者"这个模式是成立的。Anthropic 做的事情本质上是：把 LSP 中的 `textDocument/completion` 替换为 `tools/call`，把 `textDocument/diagnostic` 替换为 `resources/read`。

#### 2.1.2 脉络二：ChatGPT Plugins 的失败——不可重蹈的覆辙（2023.03-2024.04）

ChatGPT Plugins 在 2023 年 3 月推出时被寄予厚望，但在 2024 年 4 月被正式废弃，改为 GPTs。

**失败原因清单——每一条都值得 MCP 设计者警醒：**

| 失败维度 | ChatGPT Plugins 的问题 | MCP 的应对 |
|----------|----------------------|------------|
| **开放性** | 闭源生态，只有 OpenAI 能审核和上架 Plugin | 开源协议，任何人都可以实现 MCP Server |
| **厂商绑定** | Plugin 只能用于 ChatGPT | 一次编写，任何 MCP Client 都能使用 |
| **审核机制** | 中心化人工审核，效率低 | 去中心化，Host 自行决定信任哪些 Server |
| **开发体验** | 必须使用 OpenAI 特定的 manifest 格式 | 标准 JSON-RPC，任何语言都能实现 |
| **商业模式** | 不透明，Plugin 开发者无法独立盈利 | 开源社区驱动，Server 可独立部署和商业化 |
| **社区投入** | 开发者缺乏长期投入动力（平台风险） | 开放标准，Apple/Google/Anthropic 多方参与 |

**ChatGPT Plugins 失败的深层教训：**

中心化的 AI 工具生态必然失败。因为：
1. 审核瓶颈：中心化审核无法跟上工具数量的指数增长
2. 创新抑制：平台守门人决定什么工具可以存在
3. 信任单向：用户只能信任平台，无法自主评估工具风险

MCP 的去中心化设计直接回应了这些教训——没有中心审核机构，Host 自主决定信任链，Server 可独立发布。

#### 2.1.3 脉络三：开源模型的崛起——工具的民主化需求（2023-2024）

```
2023-2024 年开源 LLM 的爆发式增长：

  Llama 2 (2023.07) → Mistral (2023.09) → Llama 3 (2024.04)
  → Qwen 2 (2024.06) → DeepSeek-V2 (2024.05) → ...

结果：企业不再绑定一个 LLM 提供商，而是在多个模型间自由切换。

但问题来了：
  · Llama 3 的工具调用格式 ≠ GPT-4 的格式 ≠ Claude 的格式
  · 每换一个模型，工具集成代码就要重写
  · 企业需要的是一个"模型无关"的工具接入层

MCP 的价值在这个时间点被急剧放大：
  → 它让企业可以"定义一次工具，所有模型共用"
  → 模型厂商自己负责适配 MCP（或通过 Host 适配）
  → 工具开发者不再需要关心"这个工具是给 GPT 用的还是 Claude 用的"
```

#### 2.1.4 三条脉络的交汇点：2024 年 11 月

```
为什么是 2024 年 11 月？

  2024.04  ChatGPT Plugins 正式关闭   ← 旧范式终结
  2024.06  Llama 3 成为企业主流选择    ← 多模型格局确立
  2024.09  社区 MCP 讨论白热化          ← 需求已迫在眉睫
  2024.11  Anthropic 正式开源 MCP      ← 新范式诞生

结论：MCP 不是谁的灵光一闪，而是三个历史趋势的必然交汇：
  ① LSP 的成功证明了协议标准化的可行性（技术基础）
  ② ChatGPT Plugins 的失败说明了中心化不可行（教训总结）
  ③ 开源模型的崛起创造了对统一接入层的刚性需求（市场需求）
```

> **面试展示金句**："如果你问 MCP 为什么在 2024 年底出现，我的回答是三条线的交汇：LSP 范式证明可行（技术线），ChatGPT Plugins 用失败证明中心化走不通（教训线），开源模型多极格局倒逼统一接入标准（需求线）。MCP 的诞生是 LSP 范式在 AI 时代的自然延伸，也是对 ChatGPT Plugins 失败模式的必然反思。"

---

**教学建议**：

1. 用一个三条时间线的并排图来可视化三脉络的交汇（建议用 Mermaid 或 ASCII 时间轴）
2. 让学生自行搜索并补充一条"LSP 之外还有哪些协议影响了 MCP 的设计"的研究
3. 重点训练学生用一句话说清楚"MCP 为什么在 2024 年底出现"——这是面试中很加分的回答

## 方向 3：深化设计权衡讨论

### 3.1 新增章节：`3.4 设计权衡：MCP 选择牺牲了什么`

**插入位置**：现有 `3.3 传输层支持` 之后，`四、底层原理` 之前。

**教学目的**：让学生从"MCP 能做什么"升级到"MCP 选择不做什么"，理解每个设计决策的 trade-off。这是区分"会用 MCP"和"理解 MCP 设计哲学"的关键。

---

#### 3.1.1 简单性与灵活性——为何只定义 3+1 个原语？

**MCP 的原语设计遵循"极简主义"：**

```
Tools    (模型控制执行)
Resources (应用控制读取)
Prompts  (用户控制交互)
Sampling (Server 反向请求 LLM)  ← 第 4 个，且很多实现不包含
```

**为什么是 3+1 而不是 10 个？——比较其他方案的"原语膨胀"：**

| 如果增加这个原语 | 实际上等价于 | 为什么不单独定义 |
|------------------|-------------|-----------------|
| `Workflows` | 多个 `tools/call` 的顺序组合 | 编排是 Host/编排框架的责任，不是协议层的事 |
| `Agents` | 带有状态和决策能力的 Server | Agent 是比 MCP 更高层的抽象（属于 A2A 的范畴） |
| `Streams` | 返回流式内容的 Resource | 已被 Streamable HTTP + 流式 Tool 结果覆盖 |
| `Plugins` | 带 UI 交互的 Tool | UI 是 Host 层的职责，MCP 只管数据通道 |

**极简设计的边界——当需求撞到边界时怎么办？**

```
MCP 原语能覆盖的                       MCP 原语力不能及的
═══════════════════                   ═══════════════════

✅ LLM 调用工具获取数据                ❌ 定义一个多 Agent 协作流程
✅ LLM 读取文件/数据库内容             ❌ 管理 Agent 之间的对话状态
✅ 用户选择提示词模板引导 LLM          ❌ 定义 UI 交互（按钮、表单）
✅ Server 请求 LLM 帮忙做推理          ❌ 定义工具的定价和计费
✅ Server 推送资源变更通知             ❌ 实现工具的 A/B 测试
```

**权衡的本质**：MCP 选择了"窄而深"——在一个明确的范围内做到极致，而不是"宽而浅"——试图覆盖所有可能的场景。每个原语都有清晰的控制方和语义边界。

> **设计哲学**："一个好的协议不是功能最多的协议，而是边界最清晰的协议。MCP 的 3+1 个原语覆盖了 LLM 与外部世界交互的四个基本方向，而把编排、UI、计费留给其他层。这种克制本身就是一种智慧。"

#### 3.1.2 标准化与性能——JSON 文本协议的代价

**代价一：序列化膨胀率**

```
同样的数据，不同序列化格式的大小对比：

  天气查询结果 → {"city":"北京","temperature":25,"humidity":45,"condition":"晴"}
  
  JSON:       ~75 bytes  (基准)
  Protobuf:   ~20 bytes  (缩小 73%)
  MessagePack: ~45 bytes (缩小 40%)

对 MCP 场景的影响评估：
  · 工具参数通常 < 1KB → JSON 的膨胀可忽略
  · 工具结果通常 < 10KB → JSON 的膨胀 < 3KB
  · 文件 Resource 内容 → 二进制 base64 编码会有 33% 膨胀 ← 唯一需要关注的场景
```

**代价二：Schema 运行时校验成本**

JSON Schema 校验是纯运行时操作，Protobuf 的编解码在编译时就确定了格式。对 MCP 的影响是：每次 `tools/call` 需要做一次 JSON Schema 校验（通常在 0.1-1ms 级别），但相比工具执行时间（50-5000ms），这个开销可以忽略。

**代价三：无原生流式分帧**

JSON-RPC 的 stdio 模式用换行符分帧，这意味着 JSON 消息不能包含未转义的换行符（不能 pretty-print）。这是一个工程约束，但通常不构成实际障碍。

**性能瓶颈的真相——在什么场景下需要重新评估？**

```
场景分析：JSON 序列化何时成为瓶颈？

  ┌─────────────────────────────────────────────────┐
  │ 场景                      序列化占比  需要优化？ │
  ├─────────────────────────────────────────────────┤
  │ 典型工具调用 (1KB 参数)     < 0.01%    否       │
  │ 大型数据库查询 (100KB 结果) < 0.1%     否       │
  │ 图片/音频返回 (1MB+)       33% (base64) 重新评估 │
  │ 高频调用 (>1000 QPS)       ~1-5%       重新评估 │
  │ 超低延迟要求 (<10ms e2e)   ~5-10%      重新评估 │
  └─────────────────────────────────────────────────┘

  需要重新评估的场景（当前 MCP 设计可能力不从心）：
  1. 高频实时数据流（如每秒数千次 stock ticker 查询）
     → 考虑 gRPC Stream 或专用二进制通道
  2. 大体积二进制传输（视频、大图片）
     → MCP 支持 Resource URI 返回 URL 引用，而非内嵌 base64
  3. 超低延迟场景（如自动驾驶中 Agent 调用传感器）
     → MCP 的设计目标本不包含硬实时场景
```

> **面试金句**："MCP 用 JSON 的性能代价换取了可调试性和低门槛。在 99% 的 AI 工具调用场景中，工具本身的执行时间（50-5000ms）远大于 JSON 的序列化开销（<1ms）。当序列化真的成为瓶颈时，MCP 的 Resource URI 机制支持返回二进制数据的 URL 引用而非内嵌 base64，绕过了这个问题。"

#### 3.1.3 安全性与便利性——Server 看不到对话历史的设计

**这是 MCP 最容易被误判为"缺陷"的设计。**

```
设计决策：MCP Server 只能看到 tools/call 的参数，看不到对话历史

  ┌─────────────────────────────────────────────────────────────┐
  │  这一设计的 ██ 安全收益                                      │
  │                                                             │
  │  1. 防止恶意 Server 窃取对话信息                             │
  │     · 对话中可能包含商业机密、个人隐私                       │
  │     · 如果 Server 能读取全量历史 → 数据泄露风险不可控       │
  │                                                             │
  │  2. 最小信息暴露原则                                         │
  │     · Server 只应该知道完成当前任务所需的最少信息            │
  │     · 这是信息安全的基本原则                                 │
  │                                                             │
  │  3. 跨 Server 的数据隔离                                     │
  │     · Server A 无法知道 Server B 之前被调用了什么            │
  │     · 防止横向越权（一个被攻破的 Server 无法获取其他 Server 的数据）│
  │                                                             │
  │  4. 简化合规审计                                             │
  │     · 每个 Server 的数据处理边界清晰                         │
  │     · GDPR/个人信息保护法的"数据最小化"合规成本低            │
  └─────────────────────────────────────────────────────────────┘

  ┌─────────────────────────────────────────────────────────────┐
  │  这一设计的 ██ 功能损失（Agentic 场景下的代价）               │
  │                                                             │
  │  1. Server 无法做"上下文感知"的工具调用                      │
  │     例：用户 10 轮对话前说"我是管理员"→ Server 不知道        │
  │     → 解决办法：Host 在 tools/call 参数中传递必要的上下文    │
  │                                                             │
  │  2. Server 无法修正之前的错误                                │
  │     例：用户发现前面的查询有问题，希望 Server 自己纠正        │
  │     → 解决办法：用户在自然语言中重新表达需求                 │
  │                                                             │
  │  3. 无法实现"记忆型"工具（如"记住我叫张三，下次别问了"）     │
  │     → 解决办法：从 MCP 职责范围中排除                        │
  │     → Server 可以维护自己的会话状态（通过 session_id）       │
  │                                                             │
  │  4. Multi-turn 推理被截断                                    │
  │     例：Server 做了第一步，LLM 根据结果要求 Server 继续      │
  │     → Server 看到的是新的 tools/call，不是"继续上次"         │
  │     → 解决办法：Server 内部维护任务状态（task_id）           │
  └─────────────────────────────────────────────────────────────┘
```

**权衡的判断**：Anthropic 的设计选择明确地将安全放在便利性之前。在实验性项目和内部工具中，对话历史隔离可能显得"不方便"。但在企业生产和合规环境中，这种隔离是"必须的"。

> **面试金句**："有人说 MCP 不够灵活，因为它让 Server 看不到对话历史。我说这恰恰是 MCP 最深思熟虑的设计——它把安全做进了架构层面，而不是事后叠加。在 AI Agent 时代，让每个工具 Server 都看到全部对话历史的风险，远大于上下文感知带来的便利。"

```
场景 4: 工具与 LLM 深度耦合（如特定模型的内部 API）
  → MCP 的设计哲学是模型无关。如果工具是某个特定模型专属的，MCP 的抽象层是多余的。

场景 5: 零网络环境 + 无法启动子进程
  → MCP 的最小运行单元是一个独立进程（Server），需要进程管理能力。

场景 6: 团队没有独立维护 MCP Server 的能力
  → MCP Server 是一个需要运维的服务。如果团队只有前端开发者，引入 MCP 会增加运维负担。

场景 7: 试用/POC 阶段，不确定工具设计是否合理
  → 先用 Function Calling 快速验证。确定工具有价值后再按 MCP 规范重构。
```

> **判断原则**：**MCP 的价值 = N×M 集成收益 - 协议引入的固定成本**。当固定成本 > 收益时，MCP 不是正确选择。

#### 4.1.1 Token 消耗的临界点计算

**核心公式**：Function Calling 和 MCP 的 Token 消耗差异取决于工具 Schema 的大小和对话轮次。

```
┌─────────────────────────────────────────────────────────────────┐
│              Token 消耗对比模型                                   │
│                                                                 │
│  Function Calling:                                               │
│  TotalTokens = SchemaSize × ConvTurns + ToolResultTokens         │
│                                                                 │
│  MCP:                                                            │
│  TotalTokens = SchemaSize × 0  + ToolResultTokens               │
│               (+ tools/list 结果不在 prompt 中，不计入)          │
│                                                                 │
│  差异 = SchemaSize × ConvTurns                                   │
│                                                                 │
│  代入典型值：                                                     │
│  · 一个中等复杂的工具 Schema ≈ 150 tokens                        │
│  · 10 个工具 ≈ 1,500 tokens/轮                                  │
│  · 平均对话 5 轮 → 7,500 tokens 差异                             │
│  · 按 GPT-4o 定价 ($2.5/1M input tokens) → $0.019/次对话        │
│                                                                 │
│  看起来差异不大？但考虑高频场景：                                  │
│  · 每日 10,000 次对话 → $190/天 → $69,350/年                    │
│  · 每日 100,000 次对话 → $1,900/天 → $693,500/年                │
│                                                                 │
│  Schema 大小更极端的情况：                                        │
│  · 复杂工具 Schema (500 tokens) × 50 个工具 = 25,000 tokens/轮  │
│  · 5 轮对话 = 125,000 tokens 差异                                │
│  · 每日 10,000 次对话 → $3,125/天 → $1.14M/年                  │
└─────────────────────────────────────────────────────────────────┘
```

**Token 消耗的临界点公式：**

```
MCP 的固定成本（一次性）：
  · tools/list 请求：~100 tokens (请求) + Schema 返回 (不计入 prompt)
  · 额外的 initialize 请求：~150 tokens
  · 总计：~250 tokens / session

Function Calling 的持续成本（每轮）：
  · SchemaTokens × ConvTurns

临界条件：MCP 开始优于 Function Calling 当：
  SchemaTokens × ConvTurns > MCP固定成本
  即：150 × T × N > 250
  即：T > 250 / (150N) ≈ 1.67/N

结论：
  · N=1 个工具 → T > 1.67 轮（几乎只要多轮对话就该用 MCP）
  · N=5 个工具 → T > 0.33 轮（任何时候 MCP 都更省 token）
  · N=10 个工具 → T > 0.17 轮（MCP 的 token 优势显著）
```

> **量化结论**：除了单轮对话 + 极少数工具的极端场景，**MCP 在 Token 消耗上几乎总是优于 Function Calling**。

### 新增 Q10：MCP 为什么选择 JSON-RPC 而不是 gRPC？

<summary>参考答案</summary>

四个核心理由：

1. **性能瓶颈不在序列化**：AI 工具调用的延迟主要由 LLM 推理（200ms+）和工具执行（50-5000ms）主导，JSON 的序列化开销（<1ms）在端到端延迟中占比 < 0.1%
2. **描述自包含性**：工具 Schema 中的 `description` 字段是 LLM 理解工具用途的核心依据，JSON 原生支持运行时可见的描述，Protobuf 的注释编译后丢失
3. **传输无关性**：gRPC 重度依赖 HTTP/2，无法支持 stdio 本地进程通信、浏览器原生连接和 FaaS 部署等 MCP 核心场景
4. **生态验证**：LSP 在数百万开发者 + 每天数十亿条消息的规模上验证了 JSON-RPC 的可行性

**面试加分**：能主动补充"什么时候 gRPC 可能更好"——高频实时数据流（>1000 QPS）或超低延迟场景（<10ms e2e）

</details>

### 新增 Q11：MCP 的诞生与 LSP 和 ChatGPT Plugins 有什么关联？

**出现频率**：★★★☆☆（考察历史视野，P7+ 常问）

<details>
<summary>参考答案</summary>

三条演进脉络的交汇：

1. **LSP 的成功（技术基础）**：LSP 验证了"JSON-RPC + N×M→N+M + 能力协商"这套范式在工具通信场景中的可行性。MCP 本质上是将 LSP 的范式移植到了 AI 工具调用领域
2. **ChatGPT Plugins 的失败（反面教训）**：中心化的 AI 工具生态必然失败——审核瓶颈、创新抑制、厂商绑定。MCP 的去中心化设计是对此的直接回应
3. **开源模型的崛起（市场需求）**：多模型格局使企业对"模型无关"的工具接入层产生刚性需求

**金句**："MCP 是 LSP 范式在 AI 时代的自然延伸，也是对 ChatGPT Plugins 失败模式的必然反思"

</details>

### 新增 Q12：MCP 选择牺牲了什么？它的设计边界在哪里？

**出现频率**：★★★★☆（考察架构思维）

<details>
<summary>参考答案</summary>

三个核心 trade-off：

1. **简单性 vs 灵活性**：只定义 3+1 个原语，牺牲了对复杂编排、UI 交互等场景的协议层支持，换取极低的学习成本和实现门槛
2. **标准化 vs 性能**：选择 JSON 文本协议，牺牲了序列化效率（vs Protobuf），换取了可调试性、人类可读性和浏览器兼容性
3. **安全性 vs 便利性**：Server 看不到对话历史，牺牲了上下文感知的能力，换取了跨 Server 的数据隔离和合规性

**MCP 力不能及的场景**：硬实时（<10ms）、高吞吐二进制流（>1000 QPS 的大文件传输）、跨 Agent 状态管理（这是 A2A 的领域）

</details>

### 新增 Q13：如何量化判断一个项目是否应该采用 MCP？

**出现频率**：★★★☆☆（考察工程决策能力）

<details>
<summary>参考答案</summary>

从四个可量化维度综合评估：

1. **Token 节省**：SchemaTokens × ConvTurns > 250（MCP 的固定成本）。5 个工具 × 3 轮对话 = 节省 2000+ tokens
2. **延迟影响**：< 10%（MCP 协议开销占端到端延迟的 < 10%，LLM 推理和工具执行是主导因素）
3. **维护成本拐点**：工具数 > 5 时 MCP 累计成本开始低于 Function Calling
4. **加权评分**：工具数量(30%) + AI应用数(20%) + 跨LLM(15%) + 团队规模(15%) + 复杂度(10%) + 安全要求(10%) > 3.5 建议用 MCP

**核心结论**：MCP 不是银弹，在单工具/单LLM/个人项目的场景中引入 MCP 反而增加复杂度。判断标准是：MCP 价值 = N×M 集成收益 - 协议引入的固定成本。

</details>

### 新增 Q14：Streamable HTTP 和 WebSocket 在 MCP 场景中如何选择？

**出现频率**：★★★☆☆（考察传输层理解）

<details>
<summary>参考答案</summary>

Streamable HTTP 是 MCP 2025 年新增的默认传输方式，优于 WebSocket 的三个关键维度：

1. **企业环境兼容**：WebSocket 的 HTTP Upgrade 在企业代理/防火墙中频繁被拒，Streamable HTTP 的标准 HTTP POST/GET 天然穿透
2. **弹性伸缩友好**：WebSocket 绑定 Pod → 需要 sticky session；Streamable HTTP 每个请求独立 → 任意路由
3. **Serverless 亲和**：WebSocket 长连接与 FaaS 冲突；Streamable HTTP Stateless 模式天然适配

**什么时候 WebSocket 更好**：需要 Server 主动向 Client 高频推送的场景（如每秒多次的资源变更推送），但 MCP 的 Resource Subscription 场景通常是分钟级的变更通知，SSE 流已足够

</details>
