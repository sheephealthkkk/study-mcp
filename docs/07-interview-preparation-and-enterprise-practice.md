## 二、基础必答题（4 题·全部背诵）

### Q1：什么是 MCP？它的核心设计目标和架构组成是什么？

**出现频率：★★★★★（几乎必考）**

<details>
<summary>参考答案</summary>

**定义**：
MCP（Model Context Protocol，模型上下文协议）是由 Anthropic 于 2024 年 11 月 25 日开源的开放标准协议，标准化了大语言模型（LLM）与外部工具、数据源和服务之间的通信规则。

**核心设计目标（四大原则）**：
1. **解耦与模块化**：将 AI 应用与工具实现解耦，双方独立演进
2. **安全性**：Server 隔离设计，不能读取对话历史或窥视其他 Server
3. **可扩展性**：功能可渐进添加，向后兼容，支持社区贡献
4. **标准化**：统一工具接入协议，消除 N×M 集成困境

**核心架构（三层模型）**：
| 层 | 职责 | 实例 |
|----|------|------|
| **Host** | 管理连接、权限控制、UI 交互 | Claude Desktop, VS Code |
| **Client** | 协议路由、消息管理、与 Server 一对一通信 | SDK 中的 Client 实例 |
| **Server** | 暴露 Tools/Resources/Prompts，提供具体能力 | 数据库查询、API 调用等 |

**加分金句**：
> "MCP 想做 AI 工具调用世界的 USB-C：一套标准，连接万物。"

> "MCP 的架构设计深受 LSP（Language Server Protocol）的影响——LSP 定义了编辑器与语言服务器的协议，MCP 定义了 AI 应用与工具服务器的协议。"

</details>

### Q2：MCP 和 Function Calling 有什么区别？什么时候用哪个？

**出现频率：★★★★★（几乎必考）**

<details>
<summary>参考答案</summary>

**本质区别**：

| 维度 | Function Calling | MCP |
|------|-----------------|-----|
| **抽象层级** | 模型层面的能力（模型会用工具） | 系统层面的协议（工具如何接入） |
| **工具定义** | 硬编码在应用代码中 | 运行时从 Server 动态发现 |
| **Schema 传输** | 每次对话携带，计入 prompt token | 前置 tools/list，一次获取后缓存 |
| **跨应用复用** | 不支持（每个应用单独对接） | 原生支持（一次编写，多处使用） |
| **N×M 问题** | 存在（N 应用 × M 工具 = N×M 套代码） | 解决（降为 N+M） |
| **流式/取消** | 依赖模型自身 | 协议原生支持 |

**选型建议**：
- **用 Function Calling**：1-2 个简单工具、单一 LLM、个人项目
- **用 MCP**：5+ 个工具、多 AI 应用共享、团队协作、需要流式/进度/取消

**加分金句**：
> "MCP 实际上是构建在 Function Calling 之上的系统级协议。Function Calling 让模型'会用工具'，MCP 让工具'能被发现和复用'。"

</details>

---

### Q3：MCP 的核心原语有哪些？各自的用途和区别？

**出现频率：★★★★★（几乎必考）**

<details>
<summary>参考答案</summary>

| 原语 | 解决什么问题 | 谁控制 | 数据流 | 典型示例 |
|------|-------------|--------|--------|----------|
| **Tools** | LLM 需要执行操作 | LLM（模型控制） | Client→Server→Client | get_weather, search_db |
| **Resources** | LLM 需要读取数据 | 应用（应用控制） | Server→Client | 文件内容、数据库记录 |
| **Prompts** | 需要标准化交互模板 | 用户（用户控制） | Server→Client→LLM | 代码审查、周报模板 |
| **Sampling** | Server 反向请求 LLM 生成 | Server（服务端控制） | Server→Client→LLM→Server | 智能摘要、中间推理 |

**Tools vs Resources 的关键差异**：
- Tools 是**写**（执行操作，不一定幂等），Resources 是**读**（获取数据，天然幂等）
- Resources 支持**订阅机制**（变更通知），Tools 不支持
- 两者不能合并——安全模型不同（Host 可能对"数据库查询"和"数据库修改"配置不同权限）

**加分金句**：
> "四种原语覆盖了 LLM 与外部交互的完整方向矩阵：Tools（写）、Resources（读）、Prompts（模板化交互）、Sampling（反向请求）。"

</details>

### Q4：MCP 基于什么底层协议？支持哪些传输方式？

**出现频率：★★★★☆（高频）**

<details>
<summary>参考答案</summary>

**底层协议**：JSON-RPC 2.0

选择理由：
1. **简单性**：比 REST 更简单，只有 4 种消息类型（Request、Response、Error、Notification）
2. **传输无关**：可运行在 stdio、HTTP、WebSocket 等任何传输层
3. **双向通信**：支持请求-响应和单向通知两种模式
4. **生态验证**：被 LSP 广泛使用和验证

**三种传输方式**：

| 传输 | 通信范围 | 适用场景 | 特点 |
|------|----------|----------|------|
| **stdio** | 本地进程间 | IDE 插件、个人工具 | 零网络配置、天然进程隔离 |
| **SSE** | 远程 HTTP | Web 客户端、内部工具 | 服务端推送、自动重连 |
| **Streamable HTTP** | 远程 HTTP | 生产环境（2025 新增，默认方式） | 连接可恢复、支持 Stateless/Stateful |

**加分金句**：
> "Streamable HTTP 是 2025 年新增的默认传输方式，它融合了 stdio 的简单性和 SSE 的流式优势，同时解决了 SSE 的连接不可恢复和 Session 管理复杂等问题。"

</details>

## 三、进阶题（4 题·理解+发挥）

### Q5：MCP 的能力协商（Capability Negotiation）机制是如何工作的？

**出现频率：★★★★☆（高频）**

<details>
<summary>参考答案</summary>

**能力协商**是 Client 和 Server 在初始化和运行时声明各自支持的功能，双方按"最小交集"原则确定可用功能集的机制。

**协商流程**：

```
阶段一：初始化协商
  Client → Server: initialize {
      protocolVersion: "2025-03-26",
      capabilities: { roots: {...}, sampling: {} }
  }
  Server → Client: initialize {
      protocolVersion: "2025-03-26",
      capabilities: {
          tools: { listChanged: true },
          resources: { subscribe: true, listChanged: true },
          prompts: {}
      }
  }

阶段二：运行时遵守
  如果 Server 未声明 resources.subscribe → Client 不应发送订阅请求
  如果 Client 未声明 sampling → Server 不应发起 createMessage 请求

阶段三：渐进式更新（2025.03 新增）
  运行时通过 notifications/capabilities/updated 动态更新能力声明
  无需重新初始化连接
```

**Client 能力示例**：`roots`（根目录管理）、`sampling`（允许 Server 反向请求 LLM）、`elicitation`（引导模式）

**Server 能力示例**：`tools.listChanged`、`resources.subscribe`、`prompts.listChanged`、`logging`

**加分金句**：
> "能力协商让 Client 和 Server 可以独立升级——新 Client 可以连接旧 Server（向下兼容），新 Server 可以服务旧 Client（渐进增强）。"

</details>

### Q6：MCP 的安全模型是怎样的？如何防止 Server 获取敏感信息？

**出现频率：★★★★☆（高频，大厂必问安全）**

<details>
<summary>参考答案</summary>

**MCP 的多层安全模型**：

**第一层：Server 隔离（架构级安全）**
- Server **看不到完整的对话历史**——只能收到当前 tools/call 的参数
- Server **不能跨 Server 窥视**——每个 Server 是独立的安全域
- Host 是唯一的信任边界——它控制 Server 的加载和权限

**第二层：传输层安全（网络安全）**
- 远程模式使用 TLS 1.3 加密通信
- 可选 mTLS（Server 和 Client 互相验证证书）
- stdio 模式下进程隔离 = 安全边界

**第三层：认证与授权（访问控制）**
- OAuth 2.0 / JWT Bearer Token（企业标准方案）
- API Key（轻量级方案）
- RBAC：按角色分配工具权限（viewer / operator / admin）
- 工具级权限：`tool:search_employees`、`tool:trigger_deployment`

**第四层：输入安全（防注入）**
- 所有工具参数通过 JSON Schema 自动校验
- 文件路径穿越防护（resolve + relative_to 白名单校验）
- SQL 参数化查询（防 SQL 注入）
- 命令参数白名单（防命令注入）

**加分金句**：
> "MCP 的安全哲学是'最小信息暴露'——Server 只应该知道完成当前工具调用所需的最小信息，不应该知道用户之前问了什么，也不应该知道其他 Server 能提供什么。"

</details>

### Q7：什么是 MCP 中的 N+1 问题？你如何设计工具来避免它？

**出现频率：★★★★☆（高频，考察实战能力）**

<details>
<summary>参考答案</summary>

**N+1 问题**：当工具按"薄 API 封装"（一个 API 端点 = 一个工具）设计时，LLM 完成一个语义任务需要大量串行调用。实际研究中薄封装模式的调用次数是领域优化方案的 **5.3 倍**。

**示例——查询"技术部成员及其最近提交"**：

薄封装（22 次调用）：
```
get_department_id("技术部")     → 1 次
list_employees(dept_id=5)      → 1 次（返回 20 人）
get_commits(employee_id=1)     → 1 次
get_commits(employee_id=2)     → 1 次
...                            → 20 次
总计：22 次调用（含探索和纠错）
```

领域优化（1 次调用）：
```
get_department_overview("技术部")
→ 返回：部门信息 + 所有成员 + 每人最近提交 + 整体统计
→ 1 次调用完成
```

**解决方案——复合工具设计三步法**：

1. **识别高频任务链**：观察哪些工具常被连续调用（如：查部门→查成员→查统计）
2. **合并为语义化操作**：用领域语言命名（`get_department_overview` 而非 `api_get_dept_with_members_and_stats`）
3. **保留原子操作作为 fallback**：复合工具不替代原子工具，两者共存

**设计原则**：
> "一个工具 = 一个人类可理解的'任务'。不要暴露底层 API 的 1:1 映射。LLM 需要的是上下文，不是原始数据。"

</details>

### Q8：MCP 的发展现状有什么问题？哪些方面可以改进？

**出现频率：★★★☆☆（考察行业视野）**

<details>
<summary>参考答案</summary>

**当前问题与改进方向**：

**1. 协议还在快速迭代中**
- 问题：从 2024-11-05 到 2025-06-18 已发布多个协议版本，变化较快
- 影响：Server 和 Client 实现需要跟踪版本更新
- 改进：期待协议稳定版本（LTS）

**2. 安全隐患**
- **工具注入攻击**：恶意 MCP Server 可能通过精心构造的工具描述诱导 LLM 执行危险操作
- **依赖链安全**：MCP Server 可能依赖大量第三方包，供应链攻击面大
- 改进：Host 端工具审查机制、Server 签名验证、沙箱执行

**3. 工具发现效率**
- 问题：工具数量多时（50+），LLM 选择正确工具的准确率下降
- 改进：分级工具目录、语义搜索、上下文感知的工具推荐

**4. 大规模部署的性能**
- 问题：多 Server、多 Client 场景下的连接管理和负载均衡
- 改进：MCP Gateway 架构、Server Pool 管理、智能路由

**5. 社区生态碎片化**
- 问题：1000+ MCP Server 质量参差不齐，缺乏标准化评测
- 改进：Server 质量认证、功能测试标准、安全审计流程

**加分金句**：
> "MCP 目前的状态类似 2016 年的 GraphQL——协议理念很好，生态正在爆发，但在稳定性和安全治理方面还需要时间沉淀。"

</details>

### Q9：请设计一个支撑 10 万并发用户的 MCP 平台架构

**出现频率：★★★☆☆（架构设计题，大厂 P7+ 常考）**

<details>
<summary>参考答案</summary>

**核心挑战**：
1. 10 万用户同时通过 AI 应用使用 MCP 工具
2. 数百个 MCP Server 的注册、发现和路由
3. 毫秒级的工具调用延迟
4. 99.99% 的可用性

**架构设计**：

```
                           ┌─────────────┐
                           │   CDN / DNS  │
                           └──────┬──────┘
                                  │
                    ┌─────────────▼─────────────┐
                    │     Global Load Balancer   │
                    │     (Anycast / GCLB)       │
                    └─────────────┬─────────────┘
                                  │
              ┌───────────────────┼───────────────────┐
              │                   │                   │
    ┌─────────▼─────────┐ ┌──────▼──────┐ ┌─────────▼─────────┐
    │  Region: us-east  │ │ Region: eu  │ │  Region: ap-south │
    │  ┌─────────────┐  │ │             │ │                   │
    │  │ MCP Gateway │  │ │             │ │                   │
    │  │ (Envoy)     │  │ │             │ │                   │
    │  └──────┬──────┘  │ │             │ │                   │
    │         │         │ │             │ │                   │
    │  ┌──────▼──────┐  │ │             │ │                   │
    │  │ MCP Server  │  │ │             │ │                   │
    │  │ Cluster     │  │ │             │ │                   │
    │  │ (K8s HPA)   │  │ │             │ │                   │
    │  └─────────────┘  │ │             │ │                   │
    └───────────────────┘ └─────────────┘ └───────────────────┘
              │                   │                   │
    ┌─────────▼───────────────────▼───────────────────▼─────────┐
    │                   服务网格 (Service Mesh)                   │
    │  ┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐  │
    │  │ 注册中心  │  │ 配置中心  │  │ 密钥管理  │  │ 链路追踪  │  │
    │  │ (Consul) │  │ (K8s CM)│  │ (Vault)  │  │ (Jaeger) │  │
    │  └──────────┘  └──────────┘  └──────────┘  └──────────┘  │
    └───────────────────────────────────────────────────────────┘
```

**关键组件**：

| 组件 | 方案 | 作用 |
|------|------|------|
| **全球负载均衡** | Cloudflare / AWS Global Accelerator | 将用户路由到最近 Region |
| **区域 Gateway** | Envoy + 自定义 MCP Filter | 认证、限流、路由、协议转换 |
| **Server 集群** | K8s Deployment + HPA | 根据 QPS 自动扩缩容 |
| **服务发现** | Consul / etcd | Server 动态注册和健康检查 |
| **缓存** | Redis Cluster | 工具列表、Resource 结果缓存 |
| **消息队列** | Kafka | 异步工具调用、削峰填谷 |
| **监控** | Prometheus + Grafana + Loki | 全链路可观测性 |

**关键数据流**：
```
1. 用户请求 → Global LB → 最近 Region
2. Region Gateway 验证 Token → 查询路由表 → 转发到目标 Server
3. Server 处理 → 结果返回 Gateway → Gateway 缓存结果 → 返回 Client
4. 异步任务走 Kafka → Worker Pool 消费 → 结果写入 Redis
```

</details>

### Q11：MCP Server 和 MCP Client 之间的连接如果中断了，协议层面如何处理？

**出现频率：★★★☆☆（考察协议理解深度）**

<details>
<summary>参考答案</summary>

**处理策略取决于传输方式**：

**stdio 模式**：
- 进程退出 → 连接断开
- Client 检测到 stdin/stdout 关闭
- Host 负责重新启动 Server 进程并重新初始化
- 不需要重连逻辑，直接重建进程

**SSE 模式**：
- SSE 长连接断开 → Client 需重新发起 GET /mcp
- 通过 SSE 的 `Last-Event-Id` 头实现事件回放
- 正在执行的工具调用不受影响（通过独立的 POST 请求）
- 重新建立 SSE 流后，通过 `resources/subscribe` 重新订阅资源

**Streamable HTTP 模式**：
- **Stateless 模式**：每个请求独立，无"连接中断"之说
  每次 POST 都是全新 HTTP 请求，天然免疫连接中断
- **Stateful 模式**：通过 `Mcp-Session-Id` 头标识会话
  如果 Server 端 Session 过期，Client 重新 initialize
  设计上推荐 Stateless 作为首选

**通用恢复流程**：
```
1. Client 检测到连接异常（超时 / EOF / 错误码）
2. Client 尝试重新连接（指数退避：1s → 2s → 4s → 8s → max 60s）
3. 重新连接成功后：
   a. 重新 initialize（协议握手 + 能力协商）
   b. 重新获取 tools/list（更新工具缓存）
   c. 重新订阅 resources/subscribe（恢复资源监听）
4. 如果有正在进行的工具调用：
   a. 调用已经丢失（无法恢复），通知 LLM 重新调用
   b. LLM 基于"工具调用失败"错误决定下一步
```

**加分金句**：
> "MCP 是无状态协议——每个请求自包含。这种设计使连接中断不会导致状态丢失（因为协议层本就没有状态），恢复代价极低。所有业务状态由 Server 自身管理，协议层不持有。"

</details>

### Q12：请对比 MCP 和传统的 API Gateway + REST 方案，为什么 MCP 更适合 AI Agent？

**出现频率：★★★☆☆（考察架构判断力）**

<details>
<summary>参考答案</summary>

| 维度 | REST API + Gateway | MCP |
|------|-------------------|-----|
| **工具发现** | 开发者手动编写 OpenAPI Spec | 协议原生 tools/list 自动发现 |
| **Schema 传输** | 每次对话需要将所有 API 定义嵌入 prompt | 一次 tools/list，结果缓存 |
| **LLM 友好度** | 需要将 HTTP 方法/状态码/错误格式翻译成 LLM 能理解的形式 | 原语（Tools/Resources/Prompts）直接对应 LLM 交互模式 |
| **流式支持** | WebSocket / SSE 需额外实现 | Streamable HTTP 原生支持 |
| **进度反馈** | 无标准，各家自定义 | notifications/progress 标准通知 |
| **取消操作** | 无标准，各家自定义 | notifications/cancelled 标准通知 |
| **资源变更订阅** | Webhook / 轮询 | resources/subscribe + notifications |
| **工具复用** | 每个 AI 应用单独对接 | 一次编写 MCP Server，任何 MCP Client 可用 |
| **安全模型** | 无对话上下文隔离概念 | Server 隔离内置（看不到对话历史） |

**核心结论**：

REST API 是为**开发者**设计的——开发者阅读 API 文档，编写调用代码。MCP 是为 **AI Agent** 设计的——Agent 自动发现工具、理解何时使用、处理错误和重试。

这不是 "MCP 替代 REST" 的问题，而是 "AI Agent 时代需要一个新的交互协议"。就像移动互联网时代诞生了 GraphQL（为移动端优化查询）一样，AI Agent 时代诞生了 MCP（为 Agent 优化工具接入）。

**加分金句**：
> "传统 API Gateway 解决的是'服务怎么找到'（服务发现），MCP Gateway 解决的是'Agent 怎么使用服务'（工具理解）。前者关注运维层面，后者关注语义层面。"

</details>

## 五、面试模拟对话

### 模拟 1：基础概念考察

```
面试官： "用几句话介绍一下 MCP。"

候选人： "MCP 是 Model Context Protocol 的缩写，由 Anthropic 于 2024 年底开源。
        它的核心定位是标准化 LLM 与外部工具之间的通信协议。
        
        我理解它解决的核心问题是 N×M 集成困境——传统模式下 N 个 AI 
        应用对接 M 个工具需要 N×M 套代码，MCP 通过统一协议将其降为 N+M。
        
        MCP 采用 Host-Client-Server 三层架构，基于 JSON-RPC 2.0 协议，
        支持 stdio、SSE 和 Streamable HTTP 三种传输方式。
        
        Server 通过三种原语暴露能力：Tools（让 LLM 能执行操作）、
        Resources（让 LLM 能读取数据）、Prompts（提供交互模板）。
        还有第四种原语 Sampling，允许 Server 反向请求 LLM 生成内容。"

面试官： "不错。那 MCP 和 Function Calling 有什么关系？"

候选人： "MCP 实际上是构建在 Function Calling 之上的系统级协议。
        Function Calling 解决的是'模型层面的能力'——让模型知道有工具可以用，
        以及如何把用户的自然语言指令转化为结构化的工具调用参数。
        
        MCP 解决的是'系统层面的标准化'——工具如何被定义、发现、管理和复用。
        
        打个比方，Function Calling 让模型学会了'使用工具'这种技能，
        MCP 则定义了'工具插头的标准接口'，让不同的工具和不同的 AI 应用
        可以自由组合，不需要每次都手动适配。"
```

### 模拟 2：架构设计考察

```
面试官： "你设计了一个有 50 个工具的 MCP Server，但用户反馈 LLM 经常
         选错工具或者需要调很多次才能完成任务。你会怎么优化？"

候选人： "这个问题有两个维度需要分析。

         第一个维度是工具粒度问题。50 个工具如果都是薄 API 封装——
         一个 API 端点对应一个工具，那 N+1 问题会非常严重。
         
         我会先做一次调用链分析：看看哪些工具经常被 LLM 连续调用，
         把它们合并为复合工具。比如'查部门 → 查成员 → 查统计'这个
         常见链合并为一个 get_department_overview。
         
         第二个维度是工具描述质量。LLM 完全靠 docstring 和参数描述
         来决定选择哪个工具。如果描述模糊，选错率就高。
         
         我会检查每个工具的 description，确保包含：
         - 工具的明确用途
         - 具体的使用场景（什么时候该用这个工具）
         - 参数的格式约束和示例
         
         合并复合工具后，工具数可能降到 25-30 个，这不仅减少了 N+1，
         还降低了 LLM 的选择难度（更少的候选 → 更高的选择准确率）。"

面试官： "好。再问一下安全性。如果这个系统要部署到生产环境，
         你会做哪些安全措施？"

候选人： "多层防护。
         
         第一层是 Server 隔离——每个 Server 只看到自己工具的参数，
         看不到对话历史和其他 Server 的数据。这是 MCP 架构自带的安全机制。
         
         第二层是认证授权——生产环境必须用 OAuth 2.0 + JWT，
         工具级别的 RBAC 控制（不是所有人都有部署权限）。
         
         第三层是输入校验——虽然是 LLM 传过来的参数，
         但必须做 SQL 注入防护、路径穿越防护等标准安全校验。
         不能因为参数来自 LLM 就信任它。
         
         第四层是可观测性——所有工具调用都记录审计日志，
         异常调用模式设置告警，便于发现和安全审查。"
```
